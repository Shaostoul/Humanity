# Hide and keep: a reported post out of view at once, a sealed copy for the hotline

**Written 20 November 2026. Status: rungs 1 to 5 built 20 November 2026 (see "Built" below): the
relay, and the screens in both apps with the owner's Export and Restore; the owner role is set in
the app (a claim code, a handover, a named successor), built the same day. Rung 6 is decided:
nothing to build (the poster is told nothing beyond the ban message, the operator, 2026-11-20).** The operator asked for it the same day
("build the hide and keep moderator action") and set its limits: "Makes sense to build the system
in. We just want to make sure the system itself can't be abused." This document plans the whole
feature so each rung built is a rung of the real thing. The law it answers to is in
[`docs/reference/findings/2026-11-20-csam-reporting.md`](../reference/findings/2026-11-20-csam-reporting.md);
what people are promised is [`docs/legal/content-policy.md`](../legal/content-policy.md), section
"What a server's operator does about a report".

## Why

In the United States a provider that reports child sexual abuse material to NCMEC's CyberTipline
must keep what it reported for one year, securely, with access limited (18 U.S.C. 2258A(h)), longer
while a government preservation request runs (2703(f)), and destroy it if law enforcement asks
(2258B(c)(2)). Today the app cannot do that: "Delete the post" on a report removes the post's row and
leaves its upload at its public address, and the ordinary Delete removes the files only that post
linked. Neither keeps anything; an operator must do it by hand on the server.

## The guarantees (the operator's seven requirements, 2026-11-20)

1. **Hide.** The post and every picture or file it links leave every view at once: the web and
   desktop chat (the relay's `Delete` broadcast), every route that serves uploads (the files leave
   the served folders), and the copies on linked servers this server controls (the federated delete
   `after_delete` already sends for an ordinary delete). Reversible: the owner can restore the post
   and lift the ban if a report proves false.
2. **Keep sealed.** Each file, and the post's own words, are sealed on the relay to the server
   OWNER's key card (their Kyber768 / ML-KEM-768 key, signed by their Dilithium3 / ML-DSA-65
   identity, checked by the relay as for every card; `docs/design/key-cards.md`). No new algorithm:
   the construction of the DM seal (Kyber768 / ML-KEM-768, BLAKE3-KDF, AES-256-GCM; the "DM E2EE" row
   of `docs/reference/cryptography.md`) with a context label of its own, recorded in that table in
   the commit that adds it. The plaintext is deleted once the sealed copy is written; the relay, other
   admins and anyone who breaks into the server hold only ciphertext, and only the owner's device can
   open it. **If the relay has no checked key card for its owner, keeping is refused**, and the admin
   screen says why in words ("This server's owner has no key card here, so a copy could not be kept
   sealed. Nothing was kept."): never a readable copy instead.
   **The one exception, said plainly: a hide during an owner change** (the third review's S3; bounded
   by the fourth review's finding 5, 2026-11-21). While the owner is handing the role over or changing
   the successor, a post hidden leaves every view at once as always, but its sealed copy WAITS: its
   files and a note of the post sit unsealed in the held folder (`.waiting-<id>`, served by nothing,
   exactly as readable on the server's disk as the post was before the hide) until the change is
   carried out, rolled back, replaced by a new begin, or runs out of time, and is then sealed to
   whoever holds the role (a copy sealed to the old recipients could not be opened by the new owner,
   and a held row added during the change rolled it back). The moderator is told so in words, every
   admin's Held copies says how many wait, and the wait has a bound: a copy waiting longer than a
   change may last (its 30-minute re-wrap window, its 60-minute acceptance window and ten minutes,
   `WAITING_CAP_MS`) is sealed at once to the current recipients, the change rolled back to let it.
   A waiting folder is complete or never made (its note is written and synced before any file
   moves); a stop part-way is finished by the next seal pass from the note, and sealing is idempotent
   by the hide's id (the held item's package is that id), so a stop never leaves a copy unsealed and
   unlisted, nor makes two held items of one hide.
3. **No viewing.** No button opens a held item, for anyone, the owner included. The only way out is
   **Export**: the owner's own device unseals the package into a file saved to disk, for upload to
   NCMEC's provider form or for the police, never shown on screen. Every export is logged.
4. **One year, then gone.** Each held item carries its delete time, 365 days after it was held; the
   expiry pass deletes the sealed files and the row. A **legal hold** (the owner, with its own end
   date) keeps it past that while a preservation request runs; a **destroy now** (the owner) deletes
   it early when law enforcement asks. Admins see how many items are held and when each expires,
   never what they contain.
5. **Accountable.** Hide and keep, restore, export, legal hold and destroy now are each a SIGNED
   moderation action through the signed moderation log (`src/relay/storage/moderation.rs`,
   `docs/design/signed_moderation_logs.md`): signed by the key that took it, visible to every admin.
   A count of items held and exported, with no details, is offered for a public transparency line.
6. **Scope.** It keeps only what the server could already see: public and members-only posts and
   the files uploaded with them. It never reaches a sealed direct message or group message, and adds
   no path that does (a report's evidence already refuses any message carrying a file).
7. **Telling the person** whose post was hidden: open, not decided here (below).

## Data

A new table, `held_items` (a plain `CREATE TABLE IF NOT EXISTS` batch of its own; BUG-046 concerns
ALTER-added columns only): `id`, `report_id`, `author_key`, `stamp`, `channel`, `file_count`,
`sealed_bytes`, `held_by`, `held_at`, `delete_after`, `legal_hold_until` (0 when none),
`exported_count`. Nothing readable about the content: the post's words go into the sealed package
with the files. The sealed packages live in `data/held/<report id>/` beside the uploads folder,
which nothing serves. The report that held them is kept as long as they are (storage/reports.rs's
90-day cull and `/reports-clear` skip a report with held items). The files' `user_uploads` rows go,
so no list shows them and no limit or sweep deletes them early.

## Questions the operator answered

- **How the owner role is set** (answered 2026-11-20: he approved the recommendation, then the named
  successor: "Might as well, just in case."). A one-time claim code the relay prints to its own log
  while no key holds the role, pasted into the app; a handover by the living owner; one named
  successor. Never an admin button, since the owner receives every held copy. Built below.
- **Telling the person** (answered 2026-11-20: he agreed to the recommendation). The poster is told
  nothing beyond what a ban already says, and never that a report went to the hotline; record in the
  CyberTipline report whether they were told. No official source read had settled it (finding 12):
  nothing in 2258A forbids or requires it; a court can order silence about legal process (2705(b));
  NCMEC's reporting API records whether the user was told. Rung 6 therefore builds nothing; the
  question to NCMEC stays drafted in `docs/legal/ncmec-esp-question-draft.md` should it ever matter.

## Open questions for the operator

- **Plaintext on the owner's device.** Export and Restore need the owner's device to unseal the
  package, so the plaintext exists there for the moment it is written to a file (Export) or uploaded
  again (Restore), never on screen. Recommendation: accept; it is the only way NCMEC or the police can
  receive it.
- **No owner key card.** Recommendation: refuse keeping and offer only the existing "Delete the
  post", saying that nothing was kept, so a server without a card never holds a readable copy.

## Built (20 November 2026)

- **Who the owner is**: the one key holding the role `owner` (`Storage::owner_card`, src/relay/storage/held.rs). With none, with two or more, or with no key card that checks out, keeping is refused with words and nothing is kept. Only a claim or a handover sets it (below).
- **Rung 1**: `hide_and_keep` in a report's decisions (src/relay/handlers/held.rs, reports.rs); the post, its pinned copy, its files from every served folder and their upload rows go; the Delete broadcast; the federated delete and the outbox scrubbed. "Delete the post" now federates its delete too. BUG-330 (the owner role was not an admin in `mod_action_refusal`) fixed with it.
- **Rung 2**: the package (`data/held/<random id>/`, part 0 the words and the file list, a part per file and poster picture), sealed by `crates/humanity-protocol/src/held_seal.rs` (ML-KEM-768, BLAKE3 `derive_key`, AES-256-GCM in 1 MiB pieces; format v2 since the successor, 2026-11-20: a part key wrapped per recipient; v3 the same day, the list of recipients authenticated, the owner review's finding 10; the "Held copies" row of cryptography.md) from the original a piece at a time into a staging folder, synced, put in place, then the rows in one transaction, then the originals deleted. A failed seal changes nothing. `held_items` keeps no readable content; the expiry pass also takes out a held file a crash left in a served folder (keyed name hashes). The folder name is the package id, not the report id.
- **Rung 3**: expiry a year after holding; a legal hold (after today, at most 366 days ahead, renewable, 0 lifts) defers it; destroy now; the report kept while its items are.
- **Rung 4**: each action a `mod_action_v1` (`hide_and_keep` on a `report`, `held_legal_hold`, `held_export`, `held_destroy`, `held_restore` on a `held` item; `expires_at` the hold's end) built and signed by the actor's app (core `moderation::HELD_ACTIONS`, its web twin in `web/shared/pq-object.js`), checked by src/relay/storage/moderation_held.rs (signature, signed by the signed-in key, this server's DID, five minutes fresh, never used before, admins and moderators for the hide, the owner alone for the rest) and recorded in `held_actions` with the signed object once carried out. Kept out of the public signed-object store (refused there, never gossiped): admins see the log through `held_list`; anyone sees counts at `GET /api/held-count`. An export grants the owner's device ten minutes to fetch the sealed parts (`GET /api/held/{id}/{part}?grant=<the export's object id>`), ciphertext only; every part route also proves its CALLER (headers `x-hos-held-key`, `-time`, `-sig`: Dilithium3 over `held_<route>:<grant>:<id>:<part>:<offset>` and the time, five minutes fresh, used once; core `held_seal::caller_purpose`) and serves only the key the grant belongs to, so a grant is no bearer token (the owner review's finding 1: an admin who was the successor could fetch and open parts under the owner's grant); only the owner is sent an export's or restore's signed object, and the data-file routes refuse `data/held` entirely; `held_restore` is refused until rung 5 builds Restore.
- **Rung 5, the screens** (both apps; native `src/gui/pages/server_settings/reports.rs` and `held.rs` with `src/net/held.rs` and `src/engine/held.rs`, the website `web/chat/chat-held.js` with `web/shared/held-seal.js`, built as DOM with no innerHTML): on an open report about a post, **Hide and keep** beside the other decisions, sending the decider's own signed action; offered only when the Reports list says the server can seal a copy (`can_keep`), otherwise the relay's own sentence, then what works instead ("Delete the post") and what to do today while setting an owner is CLI debt. **Held copies** (Server Settings, Moderator, for admins; `/held` or the Reports view's button on the website): how many are held, each one's report, who held it and when, when it is deleted, any legal hold, its size and exports, the signed log and the counts; never contents, never the package id (sent only to the owner whose key it is sealed to, never drawn), no view button for anyone. For the **owner** alone, each with a reason that is signed into the log: Legal hold (days from today, at most 366, 0 lifts), Destroy now (asks first, says it cannot be undone), Export (a chooser that says what the file is for; the owner's device fetches the sealed parts under the export's ten-minute grant and opens them straight into one stored .zip, `held-item.json` without the restore key, `post.txt`, `files/<part>-<name>`, never drawn), Restore (asks first).
- **Restore, both halves**: the relay records a signed `held_restore` as a ten-minute grant; the owner's device opens each part and streams it back in pieces under nginx's 1 MB `/api/` limit (`PUT /api/held/{id}/{part}?grant=&offset=`, `x-held-restore-key`), then `POST /api/held/{id}/restore`. The relay never trusts the device for anything but bytes: at holding it sealed a restore plan (the manifest with each file's BLAKE3 hash) under a random key kept only inside the owner's part 0 (cryptography.md, "Held copies"), so the key opens the plan, every file must match it, and the words, names and folders come from the plan. Then the files go back to their own folders, their upload rows and the post's row in one transaction, every client is sent the post again (the broadcast filters by room), the held copy is deleted. A ban is lifted by the ordinary Unban.
- **The owner counts as an admin** everywhere the relay checks for one (msg_handlers.rs `is_admin_role`, 2026-11-20): marketplace listing edit and delete, review delete, project edit and delete, the board and the knock budget. BUG-330 had fixed `mod_action_refusal` alone.
- **The claim (2026-11-20)**: while no key holds `owner`, the relay mints ONE code (64 bits from the operating system's generator, 16 hex digits), prints it to its log and writes `data/owner-claim-code.txt` (src/relay/handlers/owner.rs `mint_claim_code`). It is in no message to any client and no route's answer: the data-file routes refuse that file even to admins (BUG-346, an admin could read it there and make themselves the owner). Pasted into "Claim ownership" (Server Settings, both apps, shown only while the relay's `owner_state` says there is no owner) or typed as `/claim <code>`, it makes its bearer the owner, who counts as an admin. Every attempt is compared in constant time and the right code ALWAYS claims (the owner review's finding 4: the first version checked a server-wide count before comparing, so one key's wrong guesses kept the owner out window after window). Wrong codes are counted per key (kept across reconnects), per connection and server-wide, logged, and answered after a short pause; the counts change only the words and the pause. What an attacker can do: fill the relay's log with wrong-code lines and slow their own connections. What they cannot do: find the code (64 random bits, about 290 million years on average at a thousand guesses a second) or stop the right code from working. A composer line (or an edit) starting with `/claim`, zero-width characters ignored, any case, followed by a space, a colon, the code directly or nothing, goes to the server alone or shows the claim help in both apps, never to an open DM, group or room (finding 6; the second review's W5). Wrong codes per key are forgotten 10 minutes after their latest and at most 4,096 keys are remembered (R7). A link code redeemed by the owner's key is refused with words: the owner's key is never bound under another name (R5). The right code burns the code and deletes the file; the claim is logged (the relay's log and the `owner_log` table, key and time). The claimer's key card must have reached the server and check out, else the claim is refused with words saying how to get one (sign in again with either app) and the code keeps working. This replaced the zero-admins first-admin claim: a fresh server's first claimer becomes its owner.
- **The handover (2026-11-20)**: the owner picks a member, told apart by their KEY (the second review's W1: a relay chooses which members it lists and under what names, so a compromised one could list its own key as "Bea"): each member is listed by NAME alone, and a name an honest relay could not list (anything but 1 to 24 letters, digits, `_` or `-`, the rule relay.rs `identify` holds every name to: core `key_card::honest_name`, the website's `honestName`) shows as a refused name in words, and nothing is signed for a member listed under it, neither a handover nor a naming as successor, in both apps (the website named one as successor until the fourth review's finding 4, demo D1) (the third review's M2, 2026-11-21: a relay listed its own key as "Bea (<Bea's real fingerprint>)", and the round-3 picker showed that text before the real fingerprint). **EVERY handover and EVERY naming of a successor asks, whoever the person** (the fourth review's finding 1, 2026-11-21, the orchestrator's call: "no exemption at all"): the device draws FOUR POSITIONS of the fingerprint (core `key_card::fingerprint`, six groups of four hex digits; the website's `key-card.js fingerprint`), uniformly from the 15 sets for each ask and afresh after every change signed (core `key_card::confirm_positions`, the website's `confirmPositions`), and its words tell the owner to ask the person to read those groups of THEIR OWN fingerprint from THEIR OWN screen ("ask Bea to read you groups 1, 3, 4 and 6"), in person, or by a call or message that does not go through this server (the sixth review's L2: this server's own messages and calls are ones a relay listing its key as "Bea" answers for her), and to type what they hear; the change goes ahead only when the typed groups match the LISTED key's at those positions (core `key_card::judge_at`, the website's `judgeAt`). **The comparison runs from the person's screen to the owner's, never the other way** (the fifth review's H1, 2026-11-21): round 5 showed the listed key's whole fingerprint in the picker and told the owner to read it TO the person, so the typed groups were copied off the owner's own screen, the person could not see their own fingerprint anywhere, and a relay listing its own key as "Bea" passed with no grinding at all (the critic's demo, scratchpad critic5/fp-screen-demo.test.js). Now every person sees their own key's fingerprint in words where they look after their account (Settings > Account in the desktop app, `settings/own_fingerprint.rs`; the website's Settings page and the chat's Account and Identity menu, `own-fingerprint.js`), worked out from the device's own key at startup, never waiting on a frame, and NOWHERE ELSE (the sixth review's H1, 2026-11-21: round 6 also drew it on the check prompt, and a relay copied that line's shape into an unsigned prompt's owner name and into a plain system chat line, with its own key's fingerprint; and withholding `owner_state` left the website's menu empty). Beside it the words say "Your fingerprint is only ever shown here. A fingerprint in a chat line, a message or a prompt is never yours to read out."; the check prompt says to read the groups from Settings > Account on your own device. A check prompt is drawn only once its signed action verifies on the device and its signer is the owner the member list shows (one waiting for the list is held until it comes); anything else draws nothing and is logged; its names pass the honest-name rule or show as a refused name, and no text the relay wrote is drawn in it. Every line the relay writes into the chat (a `system` frame, also how its private lines arrive) is drawn marked "From this server:" (the website) or under the sender "From this server" (the desktop app), never in the app's own voice. The owner's page shows NO member's fingerprint, and shows the listed key's whole fingerprint only once the typed groups matched it (Check these groups). **A mismatch is a warning, not an empty field**: sixteen characters typed that are not the listed key's groups say in words "These groups do not match the key listed as Bea. The person listed may not be who you think: check with them in person or by another way", are logged (the app's log; the browser console), and refuse that key on that server (per server and key: the sixth review's L1; until the desktop app restarts, whatever servers it switches between; for 24 hours in every tab of the browser, in localStorage), with no fresh draw, so a key ground to match a few groups gets ONE ask; fewer than sixteen characters only ask for all four. The round-5 rule that never asked the same set twice running is gone (it only narrowed a grinder's next draw). The round-4 exemptions are WITHDRAWN: a friend given a friendship pass (a mutual follow is one "Follow back" on a name the relay listed, and both apps then send passes by themselves, so the relay could make its own key a "friend" listed as "Bea": the critic's demo D2 handed it the role with nothing typed), and a key confirmed earlier while the app was open (that mark only ever saved typing). **Why four groups at random positions** (the third review's M2; the arithmetic corrected by the fourth review's finding 5 and recomputed for the fifth review's H1): a grinder does not make a whole ML-DSA-65 key pair per candidate; it keeps the public matrix and the secret s2 fixed and steps one coefficient of s1, so each candidate is one column added into t and a BLAKE3 hash of the public key, about 1 to 2 microseconds on one core, and still a real key pair that can sign its card. Matching g chosen groups (16 bits each) takes about 2^(16g) candidates: two groups (2^32) 1 to 2.5 core-hours, three (2^48) about 10^5 core-hours, four (2^64) 5 to 10 billion core-hours. The round-3 rule (always the last two) fell in an hour; the round-4 rule (two groups at random positions) let a key ground on three groups pass one ask in five. The four positions are drawn on the owner's device (the relay does not learn them before the person reads them out), the person reads their REAL groups, and the app compares them with the LISTED key's: so a key ground to match g of the real person's groups passes an ask only when all four drawn are among its g, C(g,4)/15, which is 0 for three or fewer. **What remains, plainly**: a relay that grinds four of the person's groups (about 2^64 candidates, billions of core-hours) passes its one ask with probability 1/15, five groups (2^80) 1/3, only all six (2^96) always; a key not ground at all passes with probability 2^-64; and a failed ask is no longer silent, it is a warning that the person listed may not be who the owner thinks. The typed groups ARE the comparison: they come from the other person's own screen, and nothing on the owner's screen gives them away before they match. **A pinned key is NOT trusted** (the third review's W1, 2026-11-21; the round-3 text here said "trusted includes a key card pinned on first use", accepted by the orchestrator that day, and is WITHDRAWN): a pin is only the key DMs are sealed to, taken the first time this device asked for that person's card, so it may be a card the relay handed over, and both apps took into the pins every good card in ANY `key_cards` frame, asked for or not, so a relay could push its own key's card and have it "trusted"; and anyone who ever wrote to the owner was pinned. The critic's demos (scratchpad critic3-web A1, A2) handed the role, and every held copy's part keys, to the relay's own key with nothing typed. Both apps now also take into the pins only a card for a key they asked for (a request they sent, matched by key, within five minutes; web/chat/chat-key-cards.js `_sent`, src/engine/key_cards.rs `requested`), dropping and logging any other; DMs keep working, since a DM's card is always one the app asked for. The owner checks the card, types their exact name and a reason, and signs an `owner_handover` (core `moderation::OWNER_ACTIONS`; checked by `Storage::check_owner_change`: this server's DID, five minutes fresh, never used before, the target a member here, not banned, with a checked card). **A CHANGE RE-WRAPS, IT NEVER RE-ENCRYPTS** (held seal format v4, 2026-11-20, the second review; it REPLACES the re-seal flow, in which the owner's device opened every part and sealed it again, the relay was handed every restore key, and each recipient opened every copy to check it). Each part's body is sealed under its own part key, and its header carries a key commitment and wraps that key once per recipient, so the owner's device fetches each part's HEADER alone (`GET /api/held/{id}/{part}/header`, a few kilobytes), opens its own slot, wraps the same key for the new list (core `held_seal::rewrap_header`, the website's `rewrapHeader`) and sends the new header (`PUT` the same route); every request signed by the owner's own key with its domain line (`hum/held-caller/v1`, the second review's R6). The relay takes a header alone, for the number of people the change names, whose commitment is the very commitment of the header it replaces (storage/owner_handover.rs `take_new_header`, under the held-folder lock and, in handlers/owner.rs `new_header_in`, under the change slot's lock while the change is still re-wrapping and no finish is building): it never takes a body byte, so no device can change what a copy holds, and no restore key travels (part 0's body never changes). In TWO PHASES (the owner review's finding 5): the finish has the relay build each new part beside the original (the new header, then the original's body copied byte for byte from its own copy, `build_new_parts`) and change NOTHING; then each recipient of the new seal (the new owner; for a naming the owner and the successor; for a removal the owner alone) gets `owner_change_check`, carrying the owner's signed action and the change's ROUND (a fresh id per begin). Their own device checks the signed action, fetches each NEW HEADER (`GET .../rewrapped`, signed by them), opens ONLY its own slot at its place in the order the action implies, checks the key against the commitment (core `held_seal::check_header`), never reads a body, and signs an `owner_change_accept` with the digest of every header's hash and the round; the relay works out the same digest from the headers it staged (`expected_acceptance`), so an acceptance of one round never carries out another (R4). **What is built is what was checked** (the third review's S1, 2026-11-21): the finish marks the change BUILDING under the slot's lock before it checks anything, so a second finish, and any header read or sent for the change, is refused until it ends; and the carry-out, under the held-folder lock, works out the digest of what it would carry out and requires EVERY recorded acceptance to carry exactly it (the round-3 code checked `uploading()` once, built unlocked, and never compared an earlier acceptance again, so a modified owner app with two sockets could have the carried-out headers differ from what a recipient checked: `an_earlier_acceptance_is_checked_again_at_the_carry_out`). Only when every recipient has accepted does it swap every package's folder and the role in one step, logging each acceptance; a decline, a digest that does not match or 60 minutes without acceptance rolls it back with every original kept (handlers/owner_accept.rs); a post hidden meanwhile no longer rolls it back (the round-3 behaviour): its sealed copy waits and is sealed once the change ends (guarantee 2's exception, above). **Rollback and carry-out exclude each other** (R4): the pending change leaves its slot under the lock before it is carried out, and a cancel, a decline, the expiry tick or a new begin arriving meanwhile is refused with words ("too late") while the change commits; every step that writes, renames or removes in the held folder (taking a new header, building the new parts, the swap, clearing new parts, the stray sweep, destroying a copy, sealing a hidden post's copy) holds the storage's one held-folder lock; reads made for a recipient's check take none, since the carry-out re-reads under the lock what it relies on. The restore plan is copied into each new folder and synced before the synced original is set aside (the third review's S4). The swap (`owner_change_in`): a marker, the folder swaps, the held folder synced, then one transaction that compares the very SET of held items (finding 9); any failure puts everything back and keeps the marker until it has, and a stop part-way is finished or undone at the next start. The old owner becomes an admin; the successor is cleared. **The residual, said plainly**: when the owner is the only person who checks a change (a successor removal), a modified owner's app could make the owner's own new slot unopenable and accept anyway, which is the same as destroying the copies (which the owner can do openly); the bodies themselves survive byte for byte, and the owner log marks such a change "checked by the owner alone". A person asked to check learns each part's key from their own slot, but is served no ciphertext: so someone who declines (or whose change is rolled back) keeps those part keys, and should they ever get the ciphertext (a breach of the relay, say) they could open the copies. Accepted as a residual by the orchestrator, 2026-11-21: they were chosen by the owner, and the alternative (serving bodies to check) handed them the content outright. **The channel the groups are read over** (the sixth review's L2, 2026-11-21): the comparison is only as good as the way the owner hears the person. - **The named successor (2026-11-20, the operator: "Might as well, just in case.")**: the owner may name ONE member with a checked key card (`owner_successor`, signed with a typed reason, the same flow and all-or-nothing check as the handover), change them, or remove them (`owner_successor_remove`). From then on every held copy is sealed to both key cards (held seal format v4: a fresh part key per part, committed to in the header and wrapped once per recipient, each wrap binding the number of recipients and its place, so a slot stripped, added or moved makes every other slot refuse; the "Held copies" row of cryptography.md); naming or changing the successor re-wraps every copy for the new pair, and removing them re-wraps for the owner alone. The successor has NO POWERS until they hold the role: export, legal hold, destroy and restore stay the owner's (`check_held_action`), and no route serves them a held copy's bytes, not even while they check a change that names them (the second review's R2: the re-seal's check handed a successor-to-be every copy in full, and a decline left no record). Every admin sees who the successor is, which copies are sealed to them, and the owner log (claims, handovers, successor changes), in Held copies. A claim or a handover clears the successor. If the owner role is ever claimed by someone who is not the successor, copies sealed to the old owner and the successor stay as they are, and the new owner can open them only if they are that successor.
- **Removing the successor is not a revocation** (the third review's S7, 2026-11-21), said plainly beside Remove successor on the owner's screen in both apps (`owner.remove_successor_limit`): from then on every copy is wrapped for the owner alone and new copies are sealed to the owner alone, but the successor's device opened the key of every part when it checked the copies, and a copy's body never changes, so a successor who kept those keys could still open a copy they get hold of (a breach of the relay, a stolen disk). Removal stops what comes next; it does not undo what they could already open. When that matters, Destroy now deletes a copy for everyone.

## Known limits, said plainly

- An owner change's acceptance proves that the recipient's device opened every copy and found what
  was held, signed by the recipient. A recipient who signs without checking (a changed app) could
  accept garbage; that acceptance is in the owner log under their key. An owner who wants copies
  gone can already Destroy now, which is logged as such.

- Export and Restore compare the copy that opened with the item the owner chose (its package and report as the list showed them, the third review's W7, and the post's author and time, the fourth review's finding 8: one report can hold several posts, each its own held item, and each item now shows which post it is; core `held_seal::manifest_is` with `Chosen`, the website's `manifestIs`): a relay serving another item's copy, or a sibling post's, under the one clicked is refused with words, and nothing is written or sent back. The relay still chooses what the list says; the check binds what opens to what the owner saw.
- A recipient's answer to a check counts as given only once the relay acknowledges it (the third review's W5): a re-ask of the same change and round with no acknowledgement is answered again (the same decline, or the check run and signed afresh), never once acknowledged.
- A post hidden during an owner change waits UNSEALED on the server's disk (served by nothing) until the change ends, at most a change's whole life and ten minutes (about 1 hour 40 minutes, `WAITING_CAP_MS`), then is sealed to the recipients then (guarantee 2's exception). If the relay stops part-way, the next start finishes and seals it. A waiting folder an older build left with files and no note, whose post and report the relay cannot find again, is kept out of view, named in the log and counted for every admin in Held copies in words ("Not sealed and not identified"); the owner removes it on the server machine. A decided report whose hide waits is never cleared by `/reports-clear`.
- The claim code file is written 0600 on Unix (the third review's S5), readable by the relay's own user alone; on Windows it takes the data folder's permissions (the signed-in user, the administrators and SYSTEM).
- The held caller's domain line does NOT yet keep a signed chat line out (the third review's S6): a chat message may hold a newline, so a chat line whose content is a held caller's purpose is signed over the same bytes and broadcast. It closes when the relay refuses chat lines that begin with a `hum/` domain line (the signed-requests branch); the held caller then moves onto that request scheme, after both branches merge.
- A file that sat in the public uploads folder was readable on the server's disk until it was held;
  deleting it does not scrub every trace from an SSD.
- Copies already fetched by other people's devices, and by linked servers this server does not
  control, are beyond reach.
- A held post's words stay in its report's evidence (links taken out), as before hide and keep: the
  report is what the admins decided on.
- A Media item whose file a held post linked keeps its row (its file is gone); the Media page's own
  report path handles items.
- Restoring a post restores it on this server only; linked servers that dropped their copy do not
  get it back.
