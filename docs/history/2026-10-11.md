# 2026-10-11

Continues 2026-10-10 (`docs/history/2026-10-10.md`). The operator's chat report (an image viewer
behind its backdrop, a composer growing off the window, video uploads failing at 2 MB, an admin
held to 6 MB) became the upload work of v0.1483.0 and v0.1484.0, and their question "what do you

## Shipped

- **v0.1485.0, the Media page.** A page in both apps beside Watch for pictures, videos, 3D
  models and files: categories the operator chooses (members can suggest one), public or members
  only, content labels that hide an item until clicked (Spoiler, Flashing lights, Graphic; adult
  content held back pending a dated legal finding), featured items, picks, reports about a Media
  item, and an admin section with a storage meter and prune lists. Big files go up in 8 MiB pieces
  that pick up after a dropped connection or a restart. Members-only files are served only to
  members, and videos stream through ten-minute tickets so no session token is ever in an address.
  Admins and moderators can keep a great item on the server so it stops counting against its
  uploader's share. Per role, in Server Settings > Roles: the largest Media file, the largest
  private file, a daily allowance, an hourly count, and how much private files one person may hold.
  Private files (DMs and groups) now leave the server with the DM mailbox, after 30 days.
- **BUG-190, phone videos and iPhone photos keep their location: fixed.** The relay removes the
  location and camera details from MP4, MOV and 3GP videos and from HEIC and AVIF photos in place
  (no re-encode, the file's size unchanged), as it already did for JPEG, PNG, GIF and WebP. The
  same strip is ported to JavaScript for the sender's own device (not wired yet), byte-identical to
  the Rust on 9,489 test inputs.
- **Deployed the same day.** The database changes migrated as planned (a persisted-format review had
  opened a copy of a v0.1484.0-shaped database with the new code first), and the operator-approved
  nginx change went live: a zone and a location for the 8 MiB pieces, and 429 instead of 503 when a
  rate refuses, with backups of both files kept in /root.
- **The composer's hints open above it** in both apps (the Attach hint had covered the chat bar).
- **The homepage dawn clip runs 30 seconds**, the same shot and sky span at 260x, and the
  homepage links to two new Library pages in a Big Ideas category.

## Lessons

- **Four review rounds, and each found real defects, fewer each time** (relay and apps: about 25,
  then 24, then 12). The second round proved two request floods by running the committed code
  against an instant stand-in server, which no unit test had: a loop is only safe when a test
  counts its requests in a time window.
- **A spec decision ends a class of bugs that fixes keep chasing.** Cancel defects recurred in
  three rounds until the rule became "a cancel means nothing stays", enforced by the server.
- **Check the claim before writing the doc.** The interplanetary doc was wrong twice in its first
  draft (the choice notes already date forward; profile time is the server's clock), and checking
  it found BUG-191.
- **Work that spans the apps and the server goes relay first,** with the apps building against
  exact shapes written in the design doc and merging when the relay lands.

## Lessons (later)

- **A fix needs its own review.** Two rounds on the profile fixes found 14 more defects, several
  of them introduced by the first fixes (a once-per-page push that missed reconnects, a "waiting"
  bio that never matched the server's tidied copy).
- **Tests on Windows stand-ins cannot see Linux file modes.** The follower's roll back would have
  made /opt/Humanity root-only (cp -a of a folder copies its mode); only a review that walked the
  script as GNU tools run it found it. Install the script outside the checkout it changes.

## v0.1487.0 (released 2026-10-12 UTC, late evening Pacific)

- **Device-to-device big files** (the operator's answer 10), relay, desktop and website: a file too
  big for the server goes from the sender's device to the receiver's in a DM, through the
  server's own call relay unless two friends allow direct connections. A file pass (signed by the
  sender, one transfer, at most 7 days) lets the receiver dial the sender and both ask the call
  relay for that one transfer; each role has a forwarded day amount. Built in parallel by three
  agents, then three review rounds settled nine rules in files-showcase.md (a `get` adds; one
  engine per channel; early candidates kept; answer notes carry the pass; credentials need a known
  peer; the day amount; a dial names its transfer; an end is always said; a dial is an answer).
- **A real two-browser run** through a throwaway loopback relay: 20 MB through the call relay, and
  120 MB with the receiver's page reloaded mid-transfer, which resumed to Saved and Sent. That
  settled the website's 15-second "stopped or dropped?" judgement for a reload in Chromium.
- **BUG-200 fixed in both apps:** "Accept files from" is remembered per server and identity, a
  server holding no profile gets this device's choice, and on a server never seen that does hold
  one the tighter word wins (the relay now says on the person's own copy whether it holds a
  profile: `stored`).
- **Small:** a file refused on a voice-off server says so in file words; the call relay's admin
  doc covers files.

## Lessons

- **Interop needs a test of its own.** Each app was tested against its own stand-in for the other,
  and each review found the two disagreeing at the seams (a sender topping up one piece at a time,
  an answerer serving one transfer, a lost cancel stranding the other side's queue). Writing the
  rules down as numbered, testable sentences in the design doc is what made the third round small.
- **A stand-in can lie about who spoke.** The website's fake data channel logged every message
  under the page whose class made the channel, so a sender's `cancel` on a channel the receiver
  opened read as the receiver's. A test asserting "Ann said cancel" only became meaningful after
  the stand-in logged the sending page.
