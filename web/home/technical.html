Open source cooperative platform

One Rust crate. A desktop app and a server. No sign-up.

HumanityOS is a single Rust crate that compiles into two programs: a desktop application with a 3D engine and an offline-first tool suite, and a headless server, the relay, that anyone can run. Servers federate pairwise, with no central authority and no home server for your account. Your identity is a set of post-quantum keys derived on your own device from a 24-word recovery phrase: there is nothing to sign up for, and no server holds a password.

The project's own code and writing are dedicated to the public domain (CC0 1.0). Read the code, run a node, fork it, or take the parts you want.

Architecture at a glance

There is one crate at src/. No Cargo workspace, no sub-crates, no separate server repository. Cargo features decide what gets compiled in, and the same source tree produces the desktop app and the server binary. 

cargo build --release --features native                       # desktop app
cargo build --release --features relay --no-default-features  # headless server

HumanityOS              # full desktop app: renderer, game, GUI, embedded relay
HumanityOS --headless   # server only, no window, listens on :3210

Desktop app

egui immediate-mode UI over a wgpu PBR renderer, a hecs ECS, rapier3d physics and kira audio, with WebRTC (str0m) for calls, voice rooms and device-to-device files. One window holds the 3D world and the everyday tools: chat, tasks, notes, files, media, market, maps and a Library.

Relay server

axum with a WebSocket at /ws and a REST API under /api/. Storage is embedded SQLite, created on first run at data/relay.db. One UDP port carries its own STUN and call forwarder. No database server, no message broker, no outside service.

The app is a server

The relay is compiled into the desktop app too, and its Host a node section starts one from inside the app, so a household PC can host a node. The prebuilt Linux relay is a separate build without the GPU and windowing libraries.

Web frontend

Plain HTML, CSS and JavaScript served by nginx, with no framework and no bundler. The desktop app is the source of truth for every UI pattern and the web mirrors it, which is why this page is styled by the same theme tokens the app uses.

Data-driven content

Items, recipes, biomes, ships, quests and planets live in CSV, TOML, RON and JSON under data/, validated against schemas in schemas/ and hot-reloaded by a file watcher. Anything that can exist more than once is a data file, not code. Modding is editing those files.

One theme source. Design tokens live in data/gui/theme.ron. The native app reads them directly and the web stylesheet is generated from the same file, so a theme change moves both surfaces at once. Colors are never hardcoded, and a test fails the build when they are.

Identity and keys

There is no sign-up, no home server, and no password stored on any server. An identity is a set of keys derived on your own device from a 24-word recovery phrase. Servers store what you publish and verify your signatures; none of them holds anything that could be used to become you.

LayerWhat it uses
Recovery phrase 24 words from the BIP39 word list, carrying 256 bits of entropy. Those 32 bytes are the root of every key below, and the only way back into the identity. Shipped
Signing identity ML-DSA-65 (Dilithium3, FIPS 204). Its keypair comes from the 32-byte root through BLAKE3 in key-derivation mode, context hum/dilithium3/v1. The public key in hex is the account everywhere. Shipped
Encryption key ML-KEM-768 (Kyber768, FIPS 203), derived the same way with context hum/kyber768/v1. Used for direct messages, group keys and recovery pieces. Shipped
Key card The encryption key, signed by the signing identity over hum/key-card/v1\n{key}\n{kyber}\n{at}, sent when you sign in and passed between linked servers. An app seals to a person only with a key from a card it checked itself, so a server cannot hand out a key of its own; a newer card with a different key is shown as a change to accept first. Shipped
Identifier did:hum:<base58(BLAKE3(public key)[..16])>, computed from the signing key, not assigned by a registry. Every server has one too, published at /api/server-info. Shipped
Signing in Two-phase identify. The server sends a nonce, the client signs hum/identify/v1\n{nonce}\n{public key}, and the server verifies before binding the socket. Claiming a key is not enough. Shipped
Chat messages ML-DSA-65 over content\ntimestamp. The relay verifies before it stores, and refuses a message with no signature or a wrong one. Shipped
Key at rest The desktop app keeps the key in a vault: AES-256-GCM under PBKDF2-SHA-256 at 600,000 iterations, unlocked by a passphrase that never leaves the device, with optional shortcuts (the OS keychain, or the keychain plus a PIN). The website uses the same scheme once you turn on key protection; until then the key sits unwrapped in the browser's own storage. Shipped
Ed25519 The same 32-byte root, read as an Ed25519 key, gives a Solana wallet address, and it is the form the website stores the root in. It is not the chat identity. Shipped
Guardian recovery The server half is built: shares split M of N, each encrypted to a guardian's ML-KEM-768 key, kept as ciphertext, with signed requests and approvals. The apps can look a setup up but cannot create one yet. Not working yet

Client and server implementations are locked together by cross-language known-answer tests, so the browser, the desktop app and the server agree byte for byte on key derivation, the message envelope and every signed preimage on this page. The canonical inventory lives in the repository, in docs/reference/cryptography.md, and changes in the same commit as the code.

What this does not do. The platform holds no funds and moves no money: a wallet address is derived for your own use, and the market is a directory, not an escrow. Losing your recovery phrase means losing the identity; no server can give it back.

Direct messages and groups

A direct message is sealed so that the server learns neither what it says nor who sent it. Shipped

  • The envelope. ML-KEM-768 encapsulation to the recipient's key, BLAKE3 as the key derivation, AES-256-GCM for the payload, carried as {v:2, ek_ct_b64, nonce_b64, ct_b64}.
  • The sender is inside it. The sealed payload is {v:2, from, to, ts, text, sig}, signed with ML-DSA-65 over hum/dm/v2\n{from}\n{to}\n{ts}\n{text}. The recipient's app checks the signature, so authenticity is end to end and the relay neither vouches for the sender nor learns who it is.
  • A mailbox with no sender column. The relay keeps dm_mailbox (id, to_key, content, received_day): the recipient, the sealed blob and the arrival day, nothing finer. Mail expires after a server setting (30 days by default, 1 to 365), and anyone can empty their own mailbox at once.
  • Two deposits per message. One for the recipient and one in the sender's own mailbox, so the sender's other devices see what was sent.
  • Padding. The plaintext is padded to the next of 256, 1,024, 4,096, 16,384 or 32,768 bytes, so the ciphertext's length does not give away the message's. The 32,768 bucket arrived in October 2026 for household permit notes, which were past the largest bucket before.
  • History lives on your devices, encrypted at rest under a key derived from your identity (a file in the desktop app, IndexedDB in the browser). The protocol has no field that could carry an unencrypted direct message.
  • Peer-to-peer groups are signed objects. Messages are encrypted under a per-epoch AES-256 group key, sealed to each member's ML-KEM-768 key and replaced whenever membership changes, so a removed member cannot read later messages. Shipped phases 1 and 2; transport that needs no relay at all is Planned.
What a server still sees. In the moment, the relay knows which signed-in socket deposits mail, because its limits need that; it does not write it down. An operator who chose to log it going forward could, and anyone watching the wire can do traffic analysis. Those are wiretap-class exposures. A copy of the database holds sender-less ciphertext.

Friendship passes and who can reach you

The server keeps no friends or follows table. Following someone is a sealed note between the two of you, and friendship is a pass: a certificate the person you gave it to carries, which the relay checks without storing who is friends with whom. Shipped 

preimage = "hum/friend/v2\n{server}\n{issuer}\n{grantee}\n{serial}\n{may}"
server   = the relay's own did:hum
serial   = 16 random bytes, lowercase hex, chosen by the issuer
may      = sorted, comma-joined subset of: call, invite, message, trade, voice_message
pass     = {"v":2, "serial", "may", "sig": ML-DSA-65 over the preimage}
  • Checked statelessly. The relay rebuilds the words from its own facts (its DID, the person being reached as issuer, the sender's signed-in key as grantee), checks the signature, then checks that the serial has not been withdrawn. It trusts nothing the pass says about who is who.
  • Taken back by serial. Unfollow and Block send cert_revoke {serial}. The relay keeps the serial under a BLAKE3 fingerprint of the issuer's key, keyed with a secret that lives only on that machine, so a copy of the database names nobody. At most 4,096 withdrawals per person.
  • No end date. New friends get every kind except call. A pass counts as given only once the server answers dm_put_ok, and what each friend may do is synced between your own devices as a signed note to yourself, so a pass taken back on one device is never given back by another.

Who can reach me

Each person picks an audience for messages, calls and trades, and the relay enforces it at the door with the pass the sender presents.

AudienceWho gets through
NobodyNo one.
People I chooseHolders of a pass from you whose may includes this kind: a tick per friend for Messages, Calls and Trades.
FriendsHolders of any valid pass from you.
Friends and groupsFriends, plus people who share a peer-to-peer group with you.
AnyoneEveryone. A stranger spends a budget of 20 messages a day.

The defaults are friends for messages and trades and chosen people for calls, so nobody can ring you until you tick them. Admins and moderators pass through the same gates. A stranger turned away can send a contact request (5 a day): an ordinary sealed message that carries only their name and a pass for you, so accepting it lets your reply through.

Block, reports and the protected setup

  • Block. Shipped Adds the person's key (never a name) to your list, withdraws every pass you gave them and unfollows. Your app then discards everything from that key on every path: messages, contact requests, posts, calls, trades, group messages, and their figure in the game. They are not told. Your other devices learn of it from a sealed note to yourself; the server never stores who blocked whom.
  • Reports the admins can check. Shipped The reporter signs hum/report/v1\n{reporter}\n{target}\n{reason}\n{evidence_hash}\n{ts}. A direct message attached as evidence is the signed payload the reporter's app already opened; the relay re-checks the reported person's signature with itself and the reporter as the facts, and marks the item checked only then. That proves the reported person wrote exactly that text to the reporter. It does not prove the time, or that nothing was left out. Moderators are never shown who reported; admins are. Decided reports are deleted 90 days after the decision.
  • The other side of that. Every direct message you send carries your signature, so its recipient can prove you wrote it.
  • No file keys in reports. A report whose evidence holds an encrypted file's marker is refused whole and nothing of it is kept, because the marker carries the file's key and cannot be cut out without breaking the sender's signature.
  • Warnings on messages. Shipped Patterns from a data file (data/safety/warnings.json) matched on your device only, never on a server, with the same matcher in both apps.
  • A guard on your recovery phrase. Shipped Before anything you write is sent, your app checks it against your own recovery phrase, and a run of four or more of its words in order stops the send. There is no switch and no "send anyway".
  • The protected setup. Shipped A PIN lock on one device's safety settings, for a parent or carer (or anyone for themselves). The PIN is 4 to 12 digits, kept only as a PBKDF2-SHA-256 verifier on that device. The preset is a data file; the server is sent nothing but an ordinary reach setting that any adult could send. It checks no one's age, and nothing about it claims to make anyone safe.
  • Erasing data. Shipped Server admins can erase another person's data on their server, and every person can export or erase their own.

Design and as-built notes: docs/design/blocking-and-safe-mode.md.

Files, private and public

Files in private conversations

  • Encrypted on the sender's device. Shipped A fresh AES-256-GCM key per file. The ciphertext is uploaded as an inert blob, and the key, nonce and file details ride inside the sealed message, or the group's encrypted message, as a [[hum:file:v1]] marker. Picked, pasted and dropped files alike, in both apps. A marker is never sent into a public channel, and private files expire with the mailbox.
  • Who you accept files from. Shipped Nobody, Friends (the default) or Anyone you talk to. The receiving app enforces it, and the choice is published on your profile so a sender's app can say so first.
  • Kept copies. Shipped A private file you opened stays on your device, encrypted at rest under a key derived from your identity, within a size cap per device, so it still opens after the server's copy expires.

Location removed before a file leaves

Shipped Every upload path in both apps removes location and camera details on the sender's device first: JPEG, PNG, WebP and MP4-family video in both, HEIC and AVIF in the desktop app. The attach step says what the file contained ("This photo says where it was taken and which camera took it."). One switch, on by default, keeps or removes; the protected setup always removes. A file that could not be read all the way through is not sent to a public place, and in a private conversation it goes only after the sender says yes, marked for the recipient. On public uploads the relay strips again with the same rules, losslessly for pictures.

The Files page

Shipped The pictures, videos, 3D models and files the people on a server chose to show. Nothing is on it unless its uploader put it there, and nothing from a private conversation can be. Admins set the categories and members suggest them; content labels (Spoiler, Flashing lights, Graphic) hide an item until it is clicked; there are personal Picks and admin Featured items; the page and each item can be public or members only; and the page has its own storage budget, a per-person share and a meter with prune lists. Every write is signed with ML-DSA-65. Adult content is not allowed until its legal question has been researched and decided.

Resumable uploads. A file for the Files page goes up in pieces of up to 8 MiB, each written and counted before the next. After a dropped connection the app asks the server how far it got and carries on; the server checks the whole file's BLAKE3 at the end. The approach is the tus protocol's, with a small wire format of our own, so neither app needs a library. Each role has limits per file, per day and per hour.

Device-to-device big files

Shipped In a direct message, a file over the sender's private-file limit never lands on the server. It goes from the sender's device to the receiver's, while both are online, after the receiver presses Accept.

  • The offer is a sealed note: name, size, the whole file's BLAKE3, a 256 KiB piece size, and a BLAKE3 over the list of piece hashes. Each piece is checked on arrival, a bad one is asked for again, and a dropped transfer resumes from the first missing piece. Either side can pause, resume or cancel, and every end is told to the other side.
  • A file pass opens the way. The sender's app signs hum/file-pass/v1\n{server}\n{issuer}\n{grantee}\n{id}\n{expiry} (at most 7 days) into the offer. On Accept the receiver dials the sender with it; the relay checks it statelessly and gives each of the two call-relay credentials for that one transfer, and nothing else.
  • Through the server's call relay by default, so neither side learns the other's network address. Two friends who allow direct connections may connect directly (a website setting today; the desktop app always uses the relay).
  • The server pays bandwidth, not disk. Each role has a forwarded amount per day, max_forwarded_mb_per_day: 2,048 MB by default for every built-in role except Admin, which has no limit. It is counted in memory per UTC day, at most 16 file allocations per person at once. Calls and voice rooms are never counted.
  • Next for files: group transfers, pieces fetched from several people at once, and fair shares that follow the server's disk and bandwidth pool Planned, in docs/design/file-transfer-at-scale.md.

Calls and network addresses

Shipped The relay answers STUN itself and carries calls and voice rooms through itself on one UDP port (3478 by default), so people in a call see only the server's address, never each other's. By default neither app asks Google, or anyone else, for its own address, and both use relay-only connections for calls and voice rooms: nothing falls back to a direct connection.

Shipped Each person chooses how their own calls connect (2026-10-22), in Settings on both apps: Private (the default, relay only), Direct (the person's own addresses are offered too, found with the server's own STUN responder, so two Direct people can talk device to device), or Direct, also asking a public service they pick (Google's or Cloudflare's, which then sees their address). A choice covers only the chooser's address: a Private person and a Direct person connect through the relay. The protected setup is always Private. Words and the public list: data/net/call_connection.json, read by both apps.

  • A closed subset of TURN (RFC 5766: Allocate, Refresh, CreatePermission, ChannelBind, Send and Data, ChannelData) with long-term credentials. Relayed addresses are virtual, ports that are never bound, and data passes only between live allocations of the same voice room, call or file transfer. Nothing is ever sent to an address a client names.
  • Credentials come only over the signed-in socket, to someone in that room's roster, that call, or holding that file pass, from a secret made when the relay starts and never stored. A restart ends every credential.
  • Limits: 2,000 allocations in total, 16 per credential, 32 per source address, 8 KiB a packet and 1.25 MB a second per allocation. Answers to strangers are held to 20 a second per address and 1,000 a second in total.
  • The operator opens the port. The forwarder runs only on a server that offers voice, and the UDP port opens only when its operator chooses (one line in node.env for the provision script). Until then the apps say the server is not set up for calls yet.
  • Tor, optionally. A script sets up a Tor v3 onion service, so a person can reach a relay without it learning their IP address. It reaches the API, the WebSocket and /health, not the website. Partial

Operator guide: docs/admin/call-forwarder.md.

What a server holds

A relay is built so that a copy of its database says little about who talks to whom.

  • No social graph. No follows table, no direct-message table with senders, no stored friendships. The old DM graph table, plaintext buyer and seller threads and plaintext legacy groups were dropped in August 2026, with secure_delete zeroing the freed pages.
  • Fingerprints, not keys. Withdrawn passes and erased accounts are recorded as BLAKE3 fingerprints keyed with a machine-local secret (data/erased-accounts.key). Without that file they name nobody. Reports store keys, never names.
  • Backups at rest. Snapshots every 6 hours sealed with AES-256-GCM (.db.enc), plus an optional 30-minute script (openssl AES-256-CBC with PBKDF2). The key, data/backup.key, sits outside the backups folder, so backups that travel without it are ciphertext.
  • Moving a server means carrying three files together: relay.db, backup.key and erased-accounts.key.
  • Your data, your call. Anyone can export what a server holds about them and erase it. An erase is remembered for a set window, so a person's offline devices do not sign them up again.

The full account, residuals included: docs/reference/retention_and_deletion_semantics.md.

Federation

A server is a place with its own channels, members and operator. Federation is a bridge between the same room on two servers, and both operators have to opt in: a peer relationship on each side, plus a per-channel toggle. There is no global admin, no registry, and no authority that can revoke a server's membership. The operator's two servers, united-humanity.us and public.guide, federate with each other today.

  • Signed hellos. Each server has an ML-DSA-65 identity and a did:hum. A peer dials /ws and sends a hello signed over fed_hello\n{server id}\n{timestamp}; the receiving server checks that it is fresh, that its operator added that peer and granted a trust tier, and the signature against the key it pinned when the peer was added. Federated chat and server announcements are signed with the same key. Server keys moved from Ed25519 to ML-DSA-65 on 6 September 2026; Server Settings re-checks a peer's key in one click.
  • Trust is not transitive. A trusting B and B trusting C does not make A trust C. Every operator picks their own peers, so one compromised hub cannot chain into everything.
  • Trust tiers 0 to 3 record how much an operator has verified a peer, and whether that peer publicly adopted the Humanity Accord. Tiers are per operator, never global.
  • Discovery, not auto-join. GET /api/federation/servers exposes a node's peer graph, and clients render it as a browsable directory. Adding a server is always the user's choice.
  • Rooms outlive servers. The desktop app shows a room carried by two or more of your servers once, merged, in a section called Commons. Sending picks a carrier at send time, and copies that arrive through two bridges collapse on origin server, time and text.
  • Signed objects travel. Market entries, votes and other signed objects gossip between peers and are deduplicated by object id; any server can check them without trusting the one that delivered them.
  • Servers that keep themselves current. scripts/relay-follow-releases.sh runs hourly from a systemd timer: it installs only a newer release, checks its sha256, backs up the database and the program, waits for /health, and rolls everything back if the relay does not come back healthy. public.guide updates itself this way.
  • Profile replication. Not working yet Servers gossip signed profiles and refuse an unsigned one, but no app signs its profile yet, so profiles do not replicate today (BUG-191).
  • Opening federation wider. Planned The roadmap's next federation step: end-to-end federation testing, then vetted third-party peers.

Federation shares discovery, bridged rooms and signed objects. It does not hand your database to anyone. Rooms you do not federate stay on your machine.

The game: one shared ship

The same desktop app is a game engine: a wgpu PBR renderer drawing true-scale planets (chunked level-of-detail terrain, volumetric clouds, oceans), a hecs ECS and rapier3d physics. On a server, the shared world is one mothership that every player boards, and the relay is its authority.

  • The world is the ship. Shipped The relay runs the mothership the game draws, from data files: the Commons and its mess hall, First Street, and twelve homestead plots of 55 by 89 m. Crew characters work and eat aboard from the same food stores as players, on one game clock that runs in real time.
  • A plot of your own. Shipped The relay hands each player a plot and remembers it per identity and server. Plots never overlap, you spawn on your own, and neighbours' homes are drawn as shells whose doors open for others.
  • What other players are told. Shipped Another player's entity carries only a name, an appearance and a key. Nobody is told who lives on which plot. Things come into view at 250 m and leave past 300 m, and the relay answers an impossible move with a correction rather than a freeze.
  • Building through the server. Shipped Every piece placed or removed on a plot is a game_build or game_unbuild that the relay judges: the plot's holder builds there, anyone else needs a household permit, and an admin can take something down.
  • Household permits. In progress A plot's holder signs hum/permit/v2\n{server}\n{plot}\n{grantee}\n{serial}\n{expiry} to let a friend build on that plot of that server, for at most 90 days. The relay checks it statelessly against its own DID, the plot and the sender, then that the serial is not withdrawn and that the signer holds the plot now. Built so far: the v2 permit, taken back through the same withdrawal list as friendship passes; giving, renewing and taking back in the game, with Block taking back every permit given to that person; permits travelling between devices as sealed notes; the relay answering whether a held permit works now; and walking into a permitted plot. Being built now: the glue that ties these into a session, the Household card on the Home page, and the two-person proof run.
  • The fleet ledger. Shipped During early development the fleet's supplies are unlimited, and a ledger shows what each player used and contributed.

Design: docs/design/ship-homes-and-logistics.md and the current increment, docs/design/ship-homes-increment-5b-plan.md.

Designing for eight billion, and for light speed

No server could carry everyone on Earth, so the rule is that none has to. No feature may need one particular server, or a big one. Each capability has to work device to device with no server, through any small server, and across many federated ones. If a community server carries about a thousand active people, everyone is about eight million servers: a large number of servers, and a small load for each.

Rules new code follows

  1. Every protocol names the server it is on (its own did:hum), as friendship passes, file passes and plot permits already do.
  2. Nothing stores "the" server: the apps can be connected to several at once.
  3. Every limit comes from the operator's pool and the role, never a constant a big server would outgrow.
  4. Anything a person creates is signed by them and can be checked by anyone, so it can travel between servers without trusting the one that delivered it.
  5. Every new feature answers: does it work with no server, with one small one, and across many?

Planned Sealed mailboxes delivered between servers, a signed "where to reach me" record, a directory spread across servers to find a person by their key, a fan-out tree of servers for live streams, a forwarding unit for big calls, and files shared among the people who hold them.

Between planets

Light takes about 1.3 seconds each way to the Moon and 3 to 22 minutes each way to Mars, and for about two weeks every 26 months the Sun cuts Mars off entirely. Six rules follow, and each pays off on Earth first: every thing is a self-contained signed bundle; no protocol needs a round trip to work; there is no single "now" (order comes from what each author had seen, and edits merge by rule); read near you and sync across the gap; send only what the other side is missing, most important first; and say honestly where a thing is.

Run your own node

The desktop build and the server are the same program, so any computer that can run the app can host a node. A relay is one binary with an embedded database and nothing else to install. On the live server it uses about 20 MB of memory and half a percent of one core.

  1. Get the relay. Download the Linux relay build and its checksum from the latest release, or build from source on any platform, or press Host a node in the desktop app. 
    wget https://github.com/Shaostoul/Humanity/releases/latest/download/HumanityOS-relay-linux-x64
wget https://github.com/Shaostoul/Humanity/releases/latest/download/HumanityOS-relay-linux-x64.sha256
sha256sum -c HumanityOS-relay-linux-x64.sha256
chmod +x HumanityOS-relay-linux-x64 && ./HumanityOS-relay-linux-x64 --headless

PORT=3210                      # optional, default 3210
DATABASE_PATH=data/relay.db    # optional, default data/relay.db
BIND_ADDRESS=0.0.0.0           # optional; 127.0.0.1 = this computer only
  2. On a LAN it is finished right there. No domain, no certificate, no port forwarding. Everyone on the same network connects to your local address.
  3. For a public node, put your domain in node.env and run scripts/provision-vps.sh on a bare Debian 12 install. It fetches the prebuilt relay and sets up nginx, TLS, the firewall and the browser origins (ALLOWED_ORIGINS) for your domain. The floor is 1 GB RAM, 1 core and 20 GB of disk.
  4. Become the first admin by typing /claim <code> with the one-time code the relay prints on first start. From then on, administration happens inside the app; its Admin map lists every action and where it lives.
  5. Calls and big files: add HUMANITY_OPEN_CALL_PORT=1 to node.env and run the provision script again to open UDP 3478.
  6. Stay current: install the release follower's systemd timer, and the node updates itself, with a roll back if a release does not come up healthy.
  7. Your own front door: copy a homepage flavour to /var/www/humanity-site/index.html. This page is one of them.

Your server, your rules

One binary can be a chat server, a shared game world, a market directory, a file host and a backup host for other people's encrypted data. You probably do not want all of that, so the features block in data/server-config.json switches each capability on or off. 

"features": {
  "chat": true, "game": true, "market": true, "vault_backup": true,
  "uploads": true, "tasks": true, "voice": true, "live_video": true,
  "federation": true, "push": true
}

A disabled feature is refused rather than hidden: the endpoint answers 403 and names the feature, so a modified client cannot use it anyway. The live manifest is published on /api/server-info so clients and peers can see what a node offers before trying to use it. Health, identity and moderation endpoints are always served, so you cannot lock yourself out of your own machine. Turning voice off also stops the call forwarder, and with it device-to-device files.

Full walkthrough: docs/admin/SELF-HOSTING.md.

The Market is a directory of signed objects

Providers and offerings are signed objects, not rows a server owns. You sign them with the same identity you chat with, the server validates them against the public schemas in schemas/provider.toml and schemas/offering.toml, and other nodes can replicate and verify them without trusting the node that served them. Shipped

  • Only you can publish into your shop. An offering signed by a key that does not own the referenced provider entry is rejected.
  • Re-running the import is the workflow. An offering is identified by provider plus your own stable SKU, so a repeat import publishes a fresh revision instead of a duplicate. Offerings expire on a time to live, 30 days by default, so the directory does not fill with ghosts.
  • Settlement is directory-only, by design. Any other settlement mode is refused. The platform lists and introduces; it never moves money and holds no funds.
  • Every market view is a query over the same public object endpoint, so anything the app can show, a script can fetch.
curl "https://united-humanity.us/api/v2/objects?object_type=offering_v1"

Any HumanityOS node answers the same query for its own directory. Importing your own catalogue: docs/admin/market-importer.md.

Source, licence, contributing

The project's own code and writing are dedicated to the public domain under CC0 1.0. Data from outside sources keeps its own licence (OpenStreetMap map data, for example, is ODbL and credited where it is drawn); LICENSES.md lists each one, and the app shows them in Settings, Credits.

The work is done in the open and shipped in small versioned increments, each with its release notes. Humans and AI agents are both first-class contributors, and the onboarding documents say so explicitly.
