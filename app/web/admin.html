What happens if you peer with nobody

Your server works completely on its own. Accounts, chat, groups, governance and the library all run locally, and nothing your members publish leaves the machine. That is a legitimate choice for a family or a small community, not a broken state.

What you give up, precisely:

  • Federated channels. A channel marked federated has nobody to carry it to, so it behaves like an ordinary local channel.
  • Groups that span servers. P2P groups are signed objects that replicate to peers. A group whose members are all on your server is unaffected; one with a member elsewhere will not sync.
  • Civilization-scope governance. Proposals that need federation-wide quorum cannot reach it. Local-scope proposals and votes work normally.
  • Being found. Your members' profiles and DIDs resolve on your server but nowhere else, so someone on another server cannot look them up.

What does not change, and is worth knowing because it is the usual assumption: direct messages never federate anyway. A DM is deposited in a sealed mailbox on the server both people are connected to, so two people already have to use the same server to exchange DMs. Peering does not change that in either direction.

None of this is one-way. Add a peer whenever you like and the federated parts start working from that moment.

Add a peer yourself

By address if the other server is reachable on the open internet. By key if it is behind a home router: it cannot be dialed, but it can dial out, and pinning its key lets its connection be recognised. Copy the key from that server's Host Node page.

Alert channels

Where this server sends a warning when something goes wrong, such as the relay going down or the disk filling up: a phone notification through ntfy, a Discord or Slack channel, a Telegram chat, or any web address that takes a message. An address or token stays on the server; after you save it, only its last characters are shown. There is no email channel: an email service's webhook address works as a Webhook.

Continuous backup

Every change to this server's database is copied, within seconds, to a place you choose: another disk, an S3-compatible bucket, or another HumanityOS server you trust. Each copy is sealed with this server's backup key before it leaves, so the place keeping it cannot read it. If the server's machine is lost, about a minute of changes is the most that is lost, and any moment inside the history you keep can be restored.

Keep a copy of data/backup.key and data/backup-destination.secrets.json somewhere off the server: a restore needs both, and the fingerprint above tells you the key you kept is this one.

Change where the copies go

Off: nothing is copied. What was already sent stays where it is.

A folder on the server: best on another disk, or a share mounted from another machine. A folder on the same disk as the database does not survive that disk failing.

Any S3-compatible storage: a provider's bucket, or your own (Garage and MinIO are free software). Leave the key fields empty to keep the saved ones.

Another HumanityOS server keeps the copies. First give its admin this server's backup sending key (below, under Keep other servers' backups here): they add it on their server, with the space they give you. Then enter that server's address here and save.

Alerts go to the alert channels in data/alert-channels.secrets.json (ntfy, Discord, Telegram, a webhook). This panel always shows the state.

Keep other servers' backups here

Other HumanityOS servers can keep their continuous backup here, sealed with their own keys: this server stores ciphertext it cannot read. Each one you add gets the space you give it, and this server also refuses copies once its own disk is 90% full.
